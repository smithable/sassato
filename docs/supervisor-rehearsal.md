# A disposable rehearsal for supervisor retirement and recovery

**Design proposal.** An unattended rehearsal would exercise the installed provider CLI through two generations before an operator spends time on the attended trial. The attended controller keeps its operator prompt. The rehearsal has a separate entry point, database and evidence type.

## Admission and authority

The trusted container launcher creates fresh PID, mount, user and network namespaces, a private cgroup, a read-only image pinned by digest, and new anonymous tmpfs volumes for the store and checkout. It runs from a reviewed image for one source commit. Its interface accepts a provider and test case. It has no arguments for a database, role, checkout, host mount, command or executable. An existing database, backup, host home, runtime socket or worktree cannot be supplied through its interface. Clear inherited environment, including database and provider overrides. The operator alone controls the launcher and its credential input.

A separate controller build for the rehearsal contains the scripted approver. The production binary has no parser, import or fallback that could select it. Before starting a provider, the rehearsal controller must authenticate its inherited private bootstrap channel to the launcher, check the expected namespace/cgroup and mount identities, and verify the mount allowlist. A container marker, environment variable, SQLite flag or path prefix alone is insufficient. The launcher provisions the store volume empty and gives exclusive write access to the controller. The controller opens a new database exclusively relative to the pinned volume directory, refuses links and existing entries, creates a random workspace and two fresh role identities, and binds enrollment to that run. No store import or role lookup by user-supplied name. Workers access only the narrow per-generation operations via a broker that validates the existing token, ancestry and reservation guards. They cannot write controller state or mint approval records.

For a crash test the launcher survives, retains the private channels/volume handles and permits exactly one controller replacement in the same run. Reopen only the pinned database identity with the original run binding and enrollment. Do not bootstrap again. Loss of the launcher or a changed identity ends the run as incomplete. At retirement, reconcile ownership and readiness, wait for every tool, helper and waiter, record the exact proposal digest, issue one scripted approval for that generation, then revalidate as in the attended controller. A changed observation or restart invalidates it. Keep an observed shell or helper alive in a negative case and require refusal.

## Provider access and limits

A **human-only provisioning step** precedes any real CLI run. Johan supplies a disposable, revocable credential through a secret input accessible only to the provider bootstrap process. The mount is read-only and memory-backed, excluded from worker tool environments, evidence, image layers and logs. A read-only mount alone cannot prevent a process with the same identity reading a secret. Require a tested process/UID boundary separating provider authentication from model-issued commands and a redaction test with a synthetic secret. If the installed CLI needs to persist refreshed credentials, exposes a bearer in tool environments or shares readable auth state with tools, leave that provider attended.

| Provider | Candidate and condition for enabling |
| --- | --- |
| Codex | Installed login help offers device authorization, API-key stdin and access-token stdin. Johan can perform a disposable device login himself in an isolated provisioning environment. Admit subscription rehearsal only after a cold start and a second generation both work with the resulting isolated read-only credential and no copied host login or shared keyring. An API key changes billing and needs a separate decision. |
| Claude | The installed CLI offers subscription-based setup-token. Johan alone would mint and revoke a dedicated token. Only enable this route if its supported bootstrap can keep the token private from tool subprocesses through both launches. The long-lived token and ordinary logged-in home are unsuitable defaults. Until that boundary is demonstrated, Claude stays attended. |

Use a nonprivileged worker, drop capabilities, disable privilege elevation, prohibit host and Docker sockets, and deny host LAN, metadata and general internet egress. Only a controlled proxy may reach the selected provider's reviewed authentication and inference endpoints. Provider helpers, git hooks, MCP configuration and plugins from host homes do not enter the image. Allow a private writable checkout, scratch and ephemeral provider runtime. Export only bounded, schema-checked evidence through the launcher. Keep one heavy run across the machine. Proposed starting budget per two-generation case is 8k–16k aggregate input plus output tokens, with a hard ceiling of 24k including retries and cached input. Reserve a worst-case turn before dispatch, constrain its output, account across both generations and terminate at 10 minutes. If trusted metering cannot bound subscription CLI usage before dispatch, run fixtures only. Runtime and turn limits alone cannot enforce a token cap. Tear down the cgroup, volumes, credential and proxy authorization on exit, failure or timeout.

## Evidence and the attended pass

Exercise normal handover, controller crash after generation 1 readiness, and shared STOP present before startup in separate fresh enrollments. STOP is private to the container. Verify one launch per generation, two distinct conversations and task commits, correct two-line file, unchanged dirty sentinel, saved-cursor mail replay, both verified exits, final reservation release and no surviving helpers. Crash recovery must reuse the existing worker and obtain fresh approval. STOP must leave zero launches. Capture versions, source and image digests, case, cgroup observations, proposal/approval/exit transitions, sentinel hash and redacted evidence summaries. Every artifact and event envelope carries an immutable rehearsal kind and run ID. Use a separate evidence store and signing identity. The acceptance verifier admits only attended records with the operator provenance it expects. A renamed or relabelled rehearsal bundle must fail verification. An incomplete run stays incomplete.

Once these cases pass on the same source commit, provider CLI version and configuration, Johan and the human assistant perform one real attended pass for the pending provider under the existing runbook. They exercise the actual operator terminal and TTY, observe and authorize each retirement, verify helper settlement and the handover evidence, and record the real installation, restart and rollback readiness. A mismatch or failed rehearsal restores the full attended investigation. The actual Claude pass and its human decision close B419/B421 and T900/T899. A rehearsal alone changes none of those records. [Attended trial and evidence](attended-supervisor.md)

Before building, review refusal cases for a pre-existing database or role, alternate mount or link, ordinary host invocation, swapped database on recovery, stale approval, leaked synthetic credential, unverifiable metering, and rehearsal evidence submitted for acceptance. No deployment or real sign-in is part of this proposal.
